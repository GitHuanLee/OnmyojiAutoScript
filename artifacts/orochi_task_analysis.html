关键结论

  • 四种身份共享“选层、锁阵容、宠物奖励、次数/时间限制、通用战斗、收尾导航”机制，差异集中在房间创建、邀请和挑战入口。
  • 最严格的进入验证出现在 wild 分支：点击挑战后必须再次确认挑战模板消失；leader/member 分支还分别验证邀请确认框和接受邀请模板。
  • 资源模板阈值主要为 0.8；锁阵容为 0.7，普通挑战按钮为 0.6，wild 挑战调用时显式使用 0.8。
  • 任务没有在 script_task.py 中直接实现底层截图或模板匹配，全部委托给 BaseTask/GameUi/GeneralBattle/GeneralInvite/GeneralRoom。

1. 当前层级：check_layer()（83–91）

layer = self.config.orochi.orochi_config.layer
pos = self.list_find(self.L_LAYER_LIST, layer)
if pos:
    self.device.click(x=pos[0], y=pos[1])
    return True
  1. 配置入口在 config.py:37–49，字段 layer: Layer 默认是 Layer.ELEVEN，即“悲鸣”。可选值包括壹至拾、悲鸣、神罚、虚无。
  2. run_leader()、run_alone()、run_wild() 分别在 128、267、319 行读取该配置并传给 check_layer(layer)；成员模式不选层，因为成员等待队长邀请。
  3. L_LAYER_LIST 是 assets.py:40 定义的纵向 OCR 列表，ROI 为 (126,107,79,593)，列表项尺寸约 78×87。list_find 找到目标文字后返回坐标。
  4. 如果 pos 存在：点击该坐标并返回 True。如果不存在：函数隐式返回 None，调用者没有 else 或失败重试；后续仍会执行锁阵容/建房。因此 OCR 失败可能导致沿用当前页面层级，这是一个需要留意的边界。

2. 锁阵容：check_lock()（93–113）

  • lock=True：截图后若已出现 I_OROCHI_LOCK 就返回；否则点击 I_OROCHI_UNLOCK，下一轮复查。
  • lock=False：逻辑相反，已出现解锁图就返回；否则点击锁定图。
  • 循环没有显式次数上限，退出保障依赖页面识别成功或框架的卡死/重复点击检测。

4. 队员流程：run_member()（215–262）

队员不执行选层和建房。每轮先处理宠物奖励，再判断次数/时间；check_then_accept() 成功就继续轮询。若在房间，调用 wait_battle(wait_time)：等待成功则执行通用战斗，等待失败则退出；若不在房间但 check_take_over_battle(False,...) 检测到队长秒开，则继续处理已开始战斗。第二个循环等待回到主界面或探索界面，并清理房间/战斗。

5. 单人流程：run_alone()（264–312）

先进入御魂页、按配置选层并按配置锁阵容。内部 is_in_orochi() 只把 I_OROCHI_FIRE 作为“仍在御魂挑战页”的标志。每轮若挑战按钮不存在就继续等待；按钮存在则点击。只有再次截图后按钮消失（283–301），才调用 run_general_battle，防止网络卡顿时误判已经进入战斗。

6. 野队公开房：run_wild()（313–394）

如果 is_in_battle(True) 已经为真，则跳过初始化，支持从中断战斗继续；否则执行选层、锁阵容、建公开房。挑战阶段（364–380）先确认不在战斗，再检查房间是否死亡；点击 I_OROCHI_WILD_FIRE 后重新截图，并要求挑战模板消失才进入通用战斗。房间死亡或邀请流程失败会把 success 置为假。

阅读代码时最容易误解的三点

  1. “当前层级”不是由识别结果回写到配置。配置层级只是目标文本；check_layer 找到就点击，找不到不会抛异常或返回后阻断流程。
  2. 次数限制依赖外部计数更新。script_task.py 只比较 current_count，战斗完成后的递增由通用战斗/任务组件负责，分析该值时应同时查看 GeneralBattle。
  3. 成功不等于每一局战斗都成功。四种流程只要正常退出并保持 success=True 就会按成功调度；房间死亡、邀请失败等显式路径才会置为失败。
